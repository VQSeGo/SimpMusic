# План оптимизации SimpMusic (форк VQSeGo)

Составлен 2026-11-10 по ветке `redesign` (`345efae5`), сборки от 2026-11-07: release APK на Redmi Note 10S
(Android 17, MT6785) и AppImage на этом ПК. Windows не измерялась.

Каждая задача ниже рассчитана на одну сессию и читается отдельно от остальных. Перед любой задачей прочитайте
раздел «Общие правила для исполнителя».

## 1. Что показали замеры

Все три жалобы в основном объясняются одной ошибкой: запрос текста песни из Spotify обновляет токен внутри
`runBlocking` на главном потоке.

| Симптом | Что измерено | Причина |
|---|---|---|
| Android: главная «висит» 3–4 с после старта | Первый кадр через 0,9 с. Затем главный поток стоит 3,6 с (`Skipped 218 frames`). Лента с сети готова через 3,0 с после старта процесса, но показана только через ~5,6 с | Задача 1 (блокировка) + задача 2 (лента запрашивается дважды, второй раз после зависания) |
| Android: при смене трека интерфейс замирает на 4–5 с, звук идёт | В журнале телефона 5 обновлений токена Spotify и ровно 5 зависаний: 242, 288, 681 (11 с, с ANR, 19:42 — случай, который запомнил пользователь), 444 и 218 кадров | Задача 1. Токен живёт 50–55 минут, поэтому зависание «случайное и редкое» |
| Desktop: запуск 7–8 с | Окно появляется через 6,5 с. Из них ~3,3 с поток интерфейса стоит на том же обновлении токена | Задача 1. Остаток (~3,2 с) разбирается в задачах 7 и 8 |

Хронология холодного старта на телефоне (один прогон, `am start -S -W`, время от создания процесса):

| t, с | Событие |
|---|---|
| 0,00 | процесс создан |
| 0,23–0,55 | `Application.onCreate`: Sentry, Koin (485 строк отладочного лога Koin), ExoPlayer, Google Cast (~0,1 с), WorkManager |
| 0,70 | создан `HomeViewModel`, ушли 5 запросов `browse` |
| 0,87 | первый кадр (`Displayed +896ms`), на экране заглушка-шиммер |
| 1,26 | главный поток входит в `getSpotifyLyrics` для восстановленного трека и блокируется |
| 2,97 | лента главной получена и разобрана в фоновом потоке, показать её некому |
| 4,84 | главный поток освободился (`Skipped 218 frames`) |
| 4,87 | главная запрашивается заново: ещё 5 запросов `browse`, снова шиммер |
| 5,58 | вторая лента разобрана, элементы появляются на экране |

Хронология старта AppImage на ПК (один прогон): запуск 0,0 → первая запись в `app.log` 1,5 с → начало запроса
текста 1,7 с → «Spotify: token refreshed» 5,2 с → окно на экране 6,5 с.

## 4. Общие правила для исполнителя

- Ветка `redesign`, мелкие коммиты. Отвечать пользователю по-русски. Подробности в `CLAUDE.md`.
- `core/` — git-сабмодуль (форк `VQSeGo/core`). Правка в `core` — это коммит внутри `core` и затем отдельный
  коммит в основном репозитории, который сдвигает указатель сабмодуля (пример в истории: `b19b704b chore(core): bump …`).
- Проверка компиляции: `./gradlew :composeApp:compileKotlinJvm --no-configuration-cache`.
- Память: 30 ГБ без подкачки. Второй экземпляр приложения не запускать, `gradlew --stop` не вызывать. Тяжёлую
  сборку запускать так:
  `systemd-run --user --scope -p MemoryMax=7G -p MemorySwapMax=0 nice -n 10 ./gradlew <задача> --no-daemon --max-workers=4 -Pkotlin.compiler.execution.strategy=in-process --no-configuration-cache`.
- AppImage: `scripts/build-appimage.sh`, результат в `~/TorvaldsVPN/Music/builds/`.
- Обработчики плеера у платформ раздельные (`MediaServiceHandlerImpl` для Android, `JvmMediaPlayerHandlerImpl`
  для desktop): правку в одном проверяйте во втором.
- Номера строк даны на коммит `345efae5` основного репозитория. Если строка уехала, ищите по приведённому тексту.
- Каждую задачу заканчивайте замером «до / после» командами из задачи 0 и записывайте цифры в таблицу раздела 7.

## 5. Задачи

### Задача 0. Метки старта и скрипты замера

**Платформа:** все. **Зависит от:** ничего.

**Зачем.** Базовые цифры уже сняты (раздел 1), но сняты по отладочным строкам лога, которые задача 4 удалит.
Нужны постоянные метки и два скрипта, чтобы любую следующую задачу можно было проверить одной командой.

**Что сделать.**

1. Метки в лог уровня Info через `com.maxrave.logger.Logger.i("Startup", …)` (уровень Info попадает и в logcat, и в
   `app.log`). В каждой метке — миллисекунды от старта процесса:
   - Android: `SystemClock.uptimeMillis() - Process.getStartUptimeMillis()`.
   - Desktop: `System.currentTimeMillis() - ManagementFactory.getRuntimeMXBean().startTime`.
   Общий помощник оформить как `expect fun millisSinceProcessStart(): Long` рядом с `getPlatform()`.
2. Точки меток:
   - `koin-done`: после `startKoin { … }` в `androidApp/src/main/java/com/maxrave/simpmusic/SimpMusicApplication.kt:64-76`
     и в `composeApp/src/jvmMain/kotlin/com/maxrave/simpmusic/DesktopApp.kt:197-208`;
   - `pre-window` (только desktop): перед `governedApplication {` в `DesktopApp.kt:280`;
   - `first-composition`: `LaunchedEffect(Unit)` в начале `App()` в `composeApp/src/commonMain/kotlin/com/maxrave/simpmusic/App.kt:144`;
   - `home-requested`: начало `getHomeItemList` в `composeApp/src/commonMain/kotlin/com/maxrave/simpmusic/viewModel/HomeViewModel.kt:186`;
   - `home-shown`: в `HomeScreen.kt` (`composeApp/src/commonMain/kotlin/com/maxrave/simpmusic/ui/screen/home/HomeScreen.kt`)
     `LaunchedEffect`, срабатывающий один раз, когда `loading == false` и список не пуст. На Android в этот же момент
     вызвать `Activity.reportFullyDrawn()` (через существующий `expect`/`actual` или `LocalActivity`), тогда система сама
     пишет в logcat строку `Fully drawn com.maxrave.simpmusic/.MainActivity: +…ms`.
3. Скрипт `scripts/perf/android-cold-start.sh`: пять раз подряд выполняет
   `adb shell am start -S -W -n com.maxrave.simpmusic/.MainActivity`, ждёт 12 с, забирает `adb logcat -d -T <метка времени>`
   и печатает для каждого прогона: `Displayed`, `Fully drawn`, метки `Startup`, строки `Choreographer: Skipped N frames`
   с N ≥ 30, число строк `curl -X POST …/browse`, общее число строк logcat процесса. В конце медианы.
4. Скрипт `scripts/perf/desktop-cold-start.sh`: проверяет, что приложение не запущено (`hyprctl clients -j` не содержит
   класса `SimpMusic`; если запущено — выйти с ошибкой), запускает AppImage через `setsid`, каждые 50 мс опрашивает
   `hyprctl clients -j` до появления окна класса `SimpMusic`, печатает время до окна и метки `Startup` из
   `~/.simpmusic/logs/app.log`, затем завершает приложение (`kill -TERM` процесса `bin/simpmusic`, ждать выхода до 15 с:
   на `SIGTERM` оно закрывается 5–9 с). Три прогона, второй запуск начинать только после выхода первого.

**Как проверить.** Оба скрипта отрабатывают и печатают цифры, близкие к разделу 1 (до задачи 1: Android `Fully drawn`
около 5,5 с и одна строка `Skipped ~218 frames`; desktop окно через ~6,5 с).

**Что может сломаться.** `reportFullyDrawn()` должен вызываться один раз за жизнь Activity. Скрипт для desktop привязан к
Hyprland; на другом композиторе нужен другой способ увидеть окно.

**Ограничение замера.** `am start -S` принудительно останавливает приложение; очередь при этом сохраняется. Телефон
должен быть разблокирован, ADB авторизован.

### Задача 1. Запрос текста Spotify убрать с главного потока

**Платформа:** общий код (`core`), действует на Android и desktop. **Статус:** подтверждено кодом и логами.
**Зависит от:** задачи 0 (для замера; саму правку можно сделать и без неё).

**Где.** `core/data/src/commonMain/kotlin/com/maxrave/data/repository/LyricsCanvasRepositoryImpl.kt:390-506`,
функция `getSpotifyLyrics`. Вызывается из `SharedViewModel.getSpotifyLyrics`
(`composeApp/src/commonMain/kotlin/com/maxrave/simpmusic/viewModel/SharedViewModel.kt:1636-1643`) в `viewModelScope`,
то есть на главном потоке.

**В чём проблема.** Это единственный сетевой `flow { }` в файле без `.flowOn(Dispatchers.IO)` (у соседних функций он
есть: строки 113, 241, 368, 547, 591). Внутри два `runBlocking` (строки 424 и 439): запрос клиентского токена и запрос
личного токена через TOTP (`core/service/spotify/src/commonMain/kotlin/com/maxrave/spotify/auth/SpotifyAuth.kt`, 3–4
сетевых обращения подряд). Пока они идут, главный поток стоит: 3,6 с при хорошей сети, 11 с и ANR при плохой.
Срабатывает при каждом холодном старте (токены сбрасываются в `CommonRepositoryImpl.kt:66-70`) и затем раз в 50–55
минут на очередной смене трека.

**Самое простое решение.**

1. Убрать обе обёртки `runBlocking { … }`, оставив их содержимое как есть: код уже находится в `suspend`-контексте
   `flow { }`, вызовы `spotify.getClientToken()` и `spotify.getPersonalTokenWithTotp(...)` — `suspend`.
2. В конец функции добавить `.flowOn(Dispatchers.IO)` по образцу соседних.
3. Удалить импорт `runBlocking`, если он больше не нужен в файле.

**Как проверить.**

- Android: `scripts/perf/android-cold-start.sh`. До: в каждом прогоне строка `Skipped 2xx frames` сразу после
  `Spotify: token refreshed`. После: строк `Skipped N frames` с N ≥ 30 нет, `Fully drawn` уменьшается примерно на 2,5 с.
- Desktop: `scripts/perf/desktop-cold-start.sh`. До: окно через ~6,5 с. После: ~3–3,5 с.
- Текст песни по-прежнему появляется (источник Spotify выбран главным у пользователя).
- Длительная проверка: за день использования в `adb logcat -d | grep -E 'Skipped [0-9]{3,} frames'` нет записей
  процесса приложения.

**Что может сломаться.** `emit` теперь выполняется в контексте IO, это допустимо для `flowOn`. Коллектор в
`SharedViewModel` остаётся на главном потоке и не меняется. Логика ветвей (`onFailure` → `emit(Resource.Error)`) не
трогается.

**Попутно проверить (10 минут).** В том же каталоге `core/data/src/commonMain/kotlin/com/maxrave/data/repository/`
найти `runBlocking` (`grep -rn runBlocking`). Места, достижимые с главного потока во время воспроизведения:
`core/data/src/androidMain/kotlin/com/maxrave/data/mediaservice/MediaServiceHandlerImpl.kt:2398-2402`
(`normalizeVolume`, чтение DataStore при каждой смене трека) и `:2816` (`endlessQueue`, только при очереди ≤ 3 треков).
Это короткие чтения из уже загруженного DataStore, отдельной задачи они не заслуживают; здесь их достаточно
перечислить в отчёте, не исправляя.

### Задача 2. Один запрос главной вместо пяти перезапусков

**Платформа:** общий код. **Статус:** подтверждено кодом и логами. **Зависит от:** 1.

**Где.** `composeApp/src/commonMain/kotlin/com/maxrave/simpmusic/viewModel/HomeViewModel.kt:93-175` (блок `init`) и
`:186-288` (`getHomeItemList`).

**В чём проблема.**

- `init` запускает пять подписок (`job1`–`job5`, строки 108-154): на регион, язык, cookie, `params` и ещё раз на cookie.
  Каждая при первом значении вызывает `getHomeItemList`, а тот отменяет предыдущий запрос (`homeJob?.cancel()`,
  строка 195).
- `job5` (строки 141-154) для вошедшего пользователя ждёт `delay(1000)` и запускает загрузку ещё раз. В logcat это видно
  как две пачки по 5 запросов `browse` и строка `Cookie changed, refreshing home`.
- `exploreChart(...)` в строке 104 запрашивает чарт отдельно, хотя чарт уже входит в `combine` (строка 205).
- `getHomeItemList` дважды читает DataStore через `runBlocking` на главном потоке (строки 189-194) и собирает строку из
  всего ответа (`Logger.d("HomeViewModel", "getHomeItemList: $result")`, строка 263) на главном потоке.

**Самое простое решение.**

1. Заменить `job1`–`job5` одной подпиской:
   `combine(location, language, cookie, params) { … }.distinctUntilChanged().collectLatest { getHomeItemList(params) }`.
   `regionCode` и `language` присваивать из значений этого `combine`.
2. Задержку `delay(1000)` оставить только для изменений cookie после первого значения (вход в аккаунт во время
   работы): первое значение обрабатывать сразу. На старте ждать нечего: cookie уже записана в клиент синхронно в
   `core/data/src/commonMain/kotlin/com/maxrave/data/repository/CommonRepositoryImpl.kt:59-63`.
3. Удалить вызов `exploreChart` из `init` (строка 104). Сам метод оставить: его вызывает экран при смене региона чарта.
4. В `getHomeItemList` перенести чтение языка и региона внутрь `viewModelScope.launch` (обычные `first()` без
   `runBlocking`).
5. Удалить строку 263.
6. `runBlocking` в строках 94-97 заменить на чтение внутри `viewModelScope.launch`.

**Как проверить.** `scripts/perf/android-cold-start.sh`: число строк `curl -X POST …/browse` за первые 12 с было 10,
должно стать 4 (лента, настроения, чарт, новинки). Метка `home-shown` уменьшается примерно на 1 с относительно замера
после задачи 1. Смена региона или языка в настройках по-прежнему перезагружает главную; кнопка обновления работает.

**Что может сломаться.** Вход в аккаунт: после входа главная должна перезагрузиться уже с cookie (для этого и оставлена
задержка на последующие изменения). Если после входа показывается гостевая лента, задержку для этой ветки увеличить
нельзя — нужно дождаться, пока `ytCookieJob` в `CommonRepositoryImpl.kt:88-105` применит cookie; проверяйте вручную
выходом и входом на desktop.

### Задача 3. Лента с прошлого запуска показывается сразу

**Платформа:** общий код (`core` и `composeApp`). **Статус:** отсутствие кэша подтверждено кодом; поведение выбрано
пользователем: показывать прошлую ленту сразу, свежей заменять по приходу. **Зависит от:** 2.

**Где.**

- `core/data/src/commonMain/kotlin/com/maxrave/data/repository/HomeRepositoryImpl.kt:64-212` (`getHomeData`), образец
  кэша там же в `getMoodAndMomentsData`, строки 286-330.
- `HomeViewModel.kt:196-287`: `combine` четырёх потоков и `loading.value = false` в строке 285.
- `composeApp/src/commonMain/kotlin/com/maxrave/simpmusic/ui/screen/home/HomeScreen.kt:512`: `Crossfade(targetState = loading)`
  заменяет весь список шиммером.

**В чём проблема.** Лента нигде не сохраняется, главная всегда ждёт сеть. `combine` выдаёт первое значение только когда
ответили все четыре запроса, поэтому лента ждёт самый медленный из них. Холодный запрос ленты на телефоне занял 2,3 с
(тёплый 0,7 с).

**Самое простое решение.**

1. Кэш. В `getHomeData` при `params == null`:
   - после успешного ответа сохранить сырой ответ: `BrowseResponse` помечен `@Serializable`
     (`core/service/kotlinYtmusicScraper/.../models/response/BrowseResponse.kt:18`), закодировать его тем же `Json` и
     записать в файл `home_cache.json` в каталоге `fileDir()` (`core/data/src/commonMain/kotlin/com/maxrave/data/io/ExpectFileSystem.kt`).
     Писать в файл, а не в DataStore: файл настроек DataStore целиком читается и переписывается при каждом изменении
     любой настройки, сотни килобайт JSON там замедлят всё приложение. `HomeItem` не `@Serializable`, поэтому кэшируется
     ответ, а не результат разбора.
   - в начале потока, до сетевого запроса, прочитать файл, разобрать тем же кодом, что и сетевой ответ (вынести разбор
     в приватную функцию), и выдать `Resource.Success`. Ошибки чтения и разбора молча игнорировать.
   - рядом хранить ключ: язык + регион + `pageId`. При несовпадении кэш не использовать. При выходе из аккаунта файл
     удалить.
   - токен продолжения из кэша не отдавать (вернуть `null`): он устаревает.
2. `HomeViewModel`: вместо одного `combine` запускать внутри `homeJob` четыре независимых `launch`, каждый пишет в свой
   `StateFlow` (`_homeItemList`, `_exploreMoodItem`, `_chart`, `_newRelease`). `loading.value = false` ставить при первом
   значении ленты. `loading.value = true` в начале `getHomeItemList` ставить только если `_homeItemList` пуст, иначе

### Задача 8. Desktop: упаковка AppImage и JVM

**Платформа:** Linux (пункт «в» применим и к Windows). **Статус:** гипотезы; делать только то, что подтвердила
задача 7. **Зависит от:** 7.

**Кандидаты.**

а) **Сжатие образа.** Подтверждено: AppImage типа 2, squashfs сжат gzip, внутри уже сжатые jar (двойное сжатие).
`desktopApp/build.gradle.kts:470-476` вызывает `appimagetool` без флага сжатия. Решение: добавить `--comp zstd`.
Делать, если вариант 2 задачи 7 быстрее варианта 1 больше чем на 0,3 с. Риск: размер файла изменится на несколько
процентов; старые системы без поддержки zstd в squashfuse (до 2019 года) не запустят.

б) **`update-desktop-database` при каждом запуске.** `AppRun` в `desktopApp/build.gradle.kts` (около строк 438-444)
каждый раз переписывает `.desktop` и обновляет базу. Решение: сравнивать содержимое и выполнять только при отличии.
Делать, если вариант 3 быстрее варианта 2 больше чем на 0,1 с.

в) **Архив классов (AppCDS).** В параметрах JVM (`conveyor.conf`, блок `jvm`, сейчас только `-Xmx512m` и `--add-opens`)
нет ни CDS, ни выбора сборщика мусора. Решение, если вариант 4 даёт больше 0,4 с: задавать `JAVA_TOOL_OPTIONS` в
`AppRun` с архивом в `~/.simpmusic/`. Известное препятствие: AppImage при каждом запуске монтируется в новый каталог
`/tmp/.mount_SimpMu<случайно>/`, а JVM проверяет совпадение путей classpath с записанными в архив, поэтому архив,
скорее всего, будет отвергаться и пересоздаваться при каждом запуске. Это нужно проверить первым делом; если так,
пункт закрыть с записью «не применимо к AppImage» и не пытаться обходить.

г) **Тяжёлое до окна.** Если отрезок запуск → `koin-done` или `koin-done` → `pre-window` длиннее 0,5 с: в
`DesktopApp.kt:270` `SharedViewModel` создаётся до окна, а `startKoin` строит ~29 объектов с `createdAtStart = true`
(`core/data/src/commonMain/kotlin/com/maxrave/data/di/DatabaseModule.kt`, `RepositoryModule.kt`), включая клиентов
`Spotify()`, `AiClient()`, `SimpMusicLyricsClient()` и загрузку libmpv. Решение: у клиентов, не нужных до первого
трека, убрать `createdAtStart`. Порядок, который нельзя менять: проверка `Desktop.isDesktopSupported()`
(`DesktopApp.kt:126`) до загрузки libmpv; проверка единственного экземпляра (`:175`) до `startKoin`.

**Как проверить.** `scripts/perf/desktop-cold-start.sh` до и после каждого пункта, собранный AppImage.

### Задача 9. Не сбрасывать токены Spotify при каждом запуске

**Платформа:** общий код (`core`). **Статус:** сброс подтверждён кодом; безопасность отказа от него — гипотеза.
**Зависит от:** 1.

сбрасывается в секундах (`epochSeconds`), а сравнивается в `LyricsCanvasRepositoryImpl.kt:415-418` в миллисекундах.

**Решение.** Удалить блок `resetSpotifyToken`. Проверку срока в `getSpotifyLyrics` оставить как есть.

**Как проверить.** Закрыть и снова открыть приложение в пределах 30 минут: в логе `Spotify tokens reused` вместо
`Spotify: token refreshed`, текст первого трека появляется сразу. Через час простоя токен обновляется и текст
появляется.

**Что может сломаться.** Причина, по которой автор оригинала добавил сброс, неизвестна. Если после перезапуска Spotify
отвечает 401 на сохранённый токен, вернуть сброс и закрыть задачу.
